# 🌐 HTTP 常见请求头小白通俗科普与 Steam 反爬 429 机理详解捏

> 本文面向所有对网络协议感到陌生的初学者或 Bot 开发者。用最贴近生活的大白话，揭开 HTTP 请求头的神秘面纱，并详细复盘我们在对抗 Steam 社区库存接口 `HTTP 429 Too Many Requests` 限流过程中的真实排查与破解过程。

---

## 一、通俗开篇：什么是 HTTP 请求头？

如果把你的机器人（或浏览器）向 Steam 服务器发请求，比作**去一家大型机构的前台办事**：
- **URL（网址）**：就像前台接待台上的**“业务窗口编号”**（比如“730 号 CS2 饰品库存查询窗口”）。
- **请求体（Body）**：如果是提交表单，就是你递给前台的**“业务申请材料”**。
- **请求头（Headers）**：就是贴在申请材料正上方的一张**“个人便签说明条”**。

这张“便签纸”上写满了对办事员（服务器）的各种交代，比如：
> *“我是谁、我带了什么设备、我能看懂哪种语言或解压格式、请把最终结果做成什么材料递给我……”*

服务器在正式处理你的业务之前，会先瞄一眼这张便签纸。如果便签纸上的信息看起来“鬼鬼祟祟”或“像个廉价机器人”，办事员可能当场就拒绝办理，甚至直接亮红灯把你轰出去！

## 二、核心请求头“三剑客”通俗拆解

在日常网络开发中，最关键、最容易被服务器安全防护系统盯上的三个请求头分别是：

### 1. `User-Agent`（用户代理 / “我是谁、用什么设备”）

- **生活比喻**：你进门时挂在胸前的**“访客工牌 / 身份证件”**。
- **作用**：告诉服务器是哪种软件、什么操作系统、什么内核版本在发请求。
- **常见类型**：
  - **真实浏览器工牌**：  
    `Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 ... Chrome/120.0.0.0 Safari/537.36`  
    *（大白话：“我是 Windows 10 电脑上的正版 Chrome 浏览器，是普通人类在上网哦！”）*
  - **脚本程序默认工牌**：  
    `axios/1.10.0`、`python-requests/2.34.2`、`curl/8.4.0`  
    *（大白话：“我是用代码写的一段自动化爬虫脚本！”）*
- **服务器态度**：许多网站的反爬防火墙一看到工牌上赫然写着 `axios` 或 `python-requests`，二话不说直接拒绝访问。

---

### 2. `Accept-Encoding`（接受的压缩编码 / “请用什么压缩包给我”）

- **生活比喻**：你告诉快递小哥：**“我懂哪种解压软件，你可以打包压缩后发给我省流量”**。
- **作用**：网页和数据体积往往很大（例如 CS2 库存有几百件饰品，原始 JSON 数据达到 250KB 以上）。为了节省网络带宽并加快传输速度，服务器可以先把数据“压缩成打包文件”，客户端收到后再在本地“解压缩”。
- **常见压缩格式**：
  - **`gzip`**：诞生了几十年的经典压缩算法（相当于电脑里最常见的普通 `.zip` 格式）。
  - **`deflate`**：另一种老式压缩算法。
  - **`br` (Brotli)**：由 Google 推出的现代超高压缩比算法（相当于现代特种高压缩格式 `.7z` / `.zst`）。目前所有主流现代浏览器（Chrome、Edge、Safari、Firefox）都原生标配支持。
  - **`zstd`**：新一代超高速压缩算法。

---

### 3. `Accept`（接受的内容类型 / “我需要什么格式的回复”）

- **生活比喻**：你在餐厅点单时交代前台：**“我要吃正餐饭菜（结构化数据），还是只要看菜单传单（网页图文）”**。
- **作用**：告诉服务器客户端期望拿到的响应数据格式（MIME 类型）：
  - **`application/json`**：我想要纯数据（API 接口专用，返回干净的 `{ "total_inventory_count": 81, "assets": [...] }`，方便程序代码直接解析）。
  - **`text/html`**：我想要渲染好的网页 HTML 页面（你在浏览器地址栏敲回车访问网站时默认发送）。
  - **`*/*`**：我不挑食，你给什么格式我都收（`curl` 默认行为）。

## 三、深度揭秘：Steam 社区 WAF 是如何利用请求头“捉爬虫”并下发 429 的？

许多开发者在用程序查询 Steam 库存时，即使挂了境外代理，依然会频繁收到刺眼的：
```text
HTTP 429 Too Many Requests (请求过多/限流)
```

大家第一反应通常是：“是不是我查太频繁了？”或者“是不是我代理节点 IP 被拉黑了？”  
但经过我们严密的控制变量 A/B 实验，真相令人大跌眼镜：**这是 Steam 针对未登录请求设置的精准反爬指纹规则！**

### 🕵️ Steam 反爬规则剖析：
1. **身份认证是第一分水岭**：
   - 如果请求携带了合法的已登录 Cookie（`steamLoginSecure`），Steam 会将你视为合法的已登录社区玩家，对网络请求具有极高的宽容度，哪怕带着老旧的 `gzip` 也能一路绿灯。
   - 如果没有登录 Cookie（绝大多数 Bot 默认都是**匿名未登录**查询），Steam 就会启动严苛的反爬风控规则。
2. **抓现行：为什么老旧压缩头是致命破绽？**
   - 绝大多数初级爬虫脚本（早期的 Python `requests`、Node.js 中的 `axios`）在未显式配置时，默认发送的压缩头都是老旧的：
     ```http
     Accept-Encoding: gzip, deflate
     ```
   - 而现代真实人类使用的浏览器，请求头一定会包含现代化的 `br` (Brotli)：
     ```http
     Accept-Encoding: gzip, deflate, br, zstd
     ```
   - **Steam 的杀手级拦截策略**：  
     > **只要是未登录的匿名请求，且请求头带有典型的老旧脚本特征（例如仅要 `gzip`，或者带有特定 Axios UA 特征），Steam WAF 直接一刀切下发 `HTTP 429 Too Many Requests`！**

### 💡 破局绝招：为什么加上 `'Accept-Encoding': 'br'` 就能秒破 429？
在插件底层代码中，我们将请求头显式指定为：
```typescript
const headers = {
  Accept: 'application/json',
  'Accept-Encoding': 'br', // 显式指定现代 Brotli 压缩！
  'User-Agent': 'Mozilla/5.0 ...' // 配合现代桌面浏览器 UA
};
```
这样一来，Steam 的防火墙在审核这张“便签纸”时，发现客户端要求使用代表现代浏览器的 **Brotli (`br`)** 压缩，判定其符合现代真实用户的请求特征，从而**完全绕过了 429 限流策略，秒回 200 OK 并完整返回库存数据！**

| :--- | :--- | :--- | :--- | :--- | :--- |
| **curl** | *(不携带)* | `curl/8.x.x` | `*/*` | **`HTTP 200 OK`** | 正常返回完整库存数据（未触发压缩防爬） |
| **Node 原生 `https`** | *(不携带 或 显式设为 `br`)* | *(不携带)* | `*/*` | **`HTTP 200 OK`** | 默认无压缩头，Steam 直接放行返回数据 |
| **现代桌面浏览器** (Chrome 等) | `gzip, deflate, br, zstd` | 浏览器完整 UA | `application/json, ...` | **`HTTP 200 OK`** | 附带完整浏览器指纹/TLS 特征，Steam 视为正常用户放行 |
| **Python 内置 `urllib.request`** | *(不携带)* | `Python-urllib/3.x` | `*/*` | **`HTTP 200 OK`** | 默认不发送压缩请求头，未踩中压缩防爬规则 |

## 五、开发者防封实战秘籍

如果你在开发其他 Steam 相关插件或爬虫，请记住以下三条黄金准则：

1. **显式要求 Brotli 压缩**：  
   永远不要完全信任 HTTP 库的默认行为，主动设置 `'Accept-Encoding': 'br'`。
2. **伪装真实浏览器 UA**：  
   主动覆盖库自带的 `User-Agent`，使用主流桌面版 Chrome 的完整 UA 字符串。
3. **已登录 Cookie 是最终护城河**：  
   当遇到特定公用代理节点被 Steam 实行了全局封禁（IP 段黑名单）时，从浏览器提取已登录的 `steamLoginSecure` 与 `sessionid` Cookie 并启用它。已认证的合法会话享有最高的 API 信任与通行优先级。
